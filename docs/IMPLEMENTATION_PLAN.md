# План реализации — Torch Automation

Цель и режимы — `PRODUCT_SPEC.md` (v2). Факты — `TECHNICAL_RESEARCH.md`, решения — `DECISIONS.md`.
Основа: аддон Meteor Client 0.5.8 + установленный у пользователя Baritone (публичный API).

## 1. Главное правило (подтверждено кодом 1.21.1)
Место (блок ног моба) **опасно**, если:
1. блок под ним проходит `allowsSpawning` хотя бы для одного «тёмного» монстра;
2. блок ног и блок над ним проходят `SpawnHelper.isClearForSpawn`;
3. хитбокс хотя бы одного вида помещается (`isSpaceEmpty(type.getSpawnBox(...))`) — проверяем zombie (0.6×1.95), spider (1.4×0.9), enderman (0.6×2.9);
4. **block light в блоке ног = 0**;
5. место входит в **зону анализа** (§3).

## 3. Зона анализа (решение проблемы «шахта под ногами»)
- Выделение (2a): границы выделения + связность от точек, куда можно дойти (недосягаемые места выводятся отдельно, а не игнорируются молча).
- Без выделения (1, 2b, 3), «Поверхность»: окно `[Y − вниз, Y + вверх]` (по умолчанию −6 / +8, настраивается), радиус (1, 3: 32; 2b: обязателен, по умолч. 48), **связность по воздуху** от игрока, опция «не глубже N блоков от поверхности» (по умолч. 3).
- «Пещера»: окно по умолчанию −24 / +16, связность обязательна, без ограничения «от поверхности».
- Y для окна в режиме 2b фиксируется в **точке старта**, а не текущей позиции (иначе зона «едет» вместе с игроком).

## 4. Алгоритмы по режимам
- **Подсветка (3):** скан окна вокруг игрока → опасные места (боксы), агрегат по чанкам (цвет по числу опасных мест), рекомендованные точки из `Planner` (маркеры).
- **Сопровождение (1):** скользящий план в окне вокруг игрока. Факел ставится, только если (а) точка входит в текущий план, (б) она в досягаемости, (в) её «вклад» ≥ порога (закрывает ≥ K опасных мест или ближайшее к игроку непокрытое место). План пересчитывается при сдвиге окна, уже стоящие факелы — часть реального света. Чтобы не ставить факелы «на краю», точки, чья зона покрытия в основном за пределами окна, откладываются до приближения игрока.
- **Автопроход 2a/2b:** полный план зоны → маршрут: следующая цель — ближайший (по пути, не по прямой) незакрытый запланированный факел → `GoalNear(точка, reach−0.5)` → установка → пересчёт. Стоп, когда план пуст или нет досягаемых точек.
- **Пещера:** тот же планировщик; кандидаты на стенах получают приоритет при равном покрытии; Baritone: `allowBreak=false`, `allowPlace=false` на время сессии (с согласия, D-5).

### 5.1 Итоги M1 (ядро)
Классы (`core/src/main/java/adentika/torch/core/`): `Dir`, `GridSnapshot`, `LightSim`, `Scope`, `Connectivity`, `SpawnModel`, `Planner`, `blocks/BlockTraits`, `blocks/Category`, `blocks/Hazard`, `blocks/CategoryResolver`.

Качество планировщика (ровный тёмный пол, без ограничения досягаемости; замер на JDK 21, этот ПК):
| Площадь | Факелов | Идеальная «решётка ромбов»* | Перерасход | Время |
|---|---|---|---|---|
| 41×41 | 9 | 9 | 0 % | ~0,14 с |
| 64×64 | 21 | 18 | +17 % | ~0,26 с |
| 128×128 | 73 | 60 | +22 % | ~0,93 с |

\* нижняя оценка для плоскости, причём допускает факелы за пределами области — реальный оптимум внутри области не меньше. Алгоритм: две детерминированные эвристики (max-gain и rarest-first) + удаление лишних факелов; берётся план с меньшим числом факелов. На произвольном рельефе «решётки» нет, поэтому используется покрытие по реальному распространению света.

Известные допущения ядра (проверяются на M2 сравнением с реальным светом игры):
1. Свет блокируется, если **одна** из двух граней полная; игра проверяет **объединение** граней (редкие комбинации двух неполных граней пропускают свет у нас, но не в игре).
2. Режим «не доверять переменным источникам» (D-21): свет на **границе** снимка берётся как есть (это может быть свет переменного источника снаружи).
3. Линия видимости при установке не проверяется в ядре (нужен raycast мира) — проверка в `TorchPlacer` на M4 с перепланированием при неудаче.
4. Неизвестные клетки не пропускают свет (консервативно: факелов может стать больше, но не меньше).
5. Память: покрытие хранится на каждого кандидата; для 128×128 укладывается в доли секунды и десятки МБ. Для больших областей — ограничение объёма (D-16) и разбиение на части в M3.

## 7. Проблемные места концепции и решения
| # | Проблема | Почему это проблема | Решение |
|---|---|---|---|
| P-1 | «Осветил зону → безопасно ходить» | Мобы появляются **не ближе 24 блоков** от игрока и **приходят** из тёмных мест вокруг зоны; мобы, появившиеся до установки факелов, никуда не деваются | Опция «буферная полоса» вокруг зоны (по умолч. 8–16 блоков, настраивается); подсказка в UI: «мобы могут прийти снаружи»; режим 3 показывает тёмное по краю |
| P-2 | Окно «вниз/вверх» в режимах 1/2b | Пещера в 3 блоках под поверхностью попадёт в окно; на холмах игрок меняет высоту и окно «прыгает» | Окно **+ связность по воздуху** от игрока + опция «не глубже N от поверхности»; для 2b окно фиксируется по точке старта |
| P-3 | Опасные места, куда нельзя дойти (крыши домов, верхушки деревьев, уступы скал) | Мобы могут там появиться, но факел не поставить / Baritone не дойдёт | Считать их отдельно («недосягаемо: N»), пытаться закрыть факелом с досягаемой позиции (свет «перетекает»), иначе показать игроку; на крышах — подсказка (нижние плиты/ступени не дают спавна) |
| P-4 | Режим 1: локальная жадность | Решения «по ходу» хуже полного плана: факелы на краях окна, лишние факелы при возврате | Скользящий план + отложенная установка краевых точек + порог вклада (§4) |
| P-5 | Режим 2b без границ | Бесконечный мир → мод может уйти далеко, потратить все факелы, попасть в опасность | Обязательные радиус, окно, лимит факелов и времени; остановка, если нет досягаемых непокрытых мест |
| P-6 | «Учитывать другие источники» — непостоянный свет | Печь/коптильня горят временно; лампа и медная лампа выключаются; свечи и костёр тушатся. Сейчас светло, ночью — нет | Опция «не доверять переменным источникам» (по умолч. вкл.): их свет не считается защитой; список блоков — в `TECHNICAL_RESEARCH` при реализации |
| P-7 | Вода | Утопленники появляются в воде; поставить факел в воду нельзя | Свет с берега проходит в воду (block light не ослабляется водой сильнее обычного — проверить на M2); места в воде показывать отдельно; профиль «вода» вкл./выкл. |
| P-8 | Объём ресурсов | Поверхность 100×100 ≈ десятки факелов; пещеры — ещё больше | Оценка числа до старта; стоп с сообщением при нехватке; лимит в 2b |
| P-9 | Серверы и античит | Режимы 1 и особенно 2 = автоматизация; на многих серверах запрещено | Предупреждение при первом включении; умеренная частота действий; никаких обходов; режим 3 работает без автоматизации |
| P-10 | Baritone ломает/строит по умолчанию | Может испортить постройки, копать в пещере | На время сессии предложить `allowBreak=false`, `allowPlace=false` с восстановлением (D-5) |
| P-11 | Подсветка «чанками» | Чанк 16×16×384 слишком крупный: в нём может быть 1 тёмное место | Два уровня: цвет чанка (сводка) + боксы отдельных мест рядом с игроком |
| P-12 | Установка и снос | Факел падает, если сломать опору; игрок/мобы ломают факелы | После установки — проверка; при повторном скане такие места снова становятся опасными и попадают в план |
| P-13 | Незагруженные чанки | Свет и блоки там неизвестны | Помечать «неизвестно», не планировать; в 2a/2b — догружать подходом |
| P-14 | Порядок обхода в 2a | Обход «по ближайшей точке» может гонять туда-обратно | Ближайшая по пути (оценка Baritone) + обход по полосам для больших областей; это эвристика |
