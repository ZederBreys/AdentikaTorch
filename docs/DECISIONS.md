# Решения — Torch Automation

Статус: **P** — предложено, ждёт подтверждения пользователя; **A** — принято (D-1…D-33 приняты пользователем 2026-10-25).

| ID | Решение | Статус | Обоснование |
|---|---|---|---|
| D-1 | Лицензия аддона — **GPL-3.0** | A | Аддон наследует классы Meteor (GPL-3.0); README Meteor требует ту же лицензию при использовании кода. См. TECHNICAL_RESEARCH §6. |
| D-2 | База — **аддон Meteor 0.5.8** (entrypoint `meteor`), а не отдельный Fabric-мод | A | Meteor уже есть у пользователя и даёт модули, настройки, keybind, рендер 3D, поиск в инвентаре, путь размещения блоков и `PathManagers`. Ядро (анализ/планировщик) держим без зависимостей от Meteor, чтобы при необходимости сделать отдельный Fabric-мод. |
| D-3 | Baritone — **не включать в JAR**, `modCompileOnly meteordevelopment:baritone:1.21.1-SNAPSHOT`, использовать установленный у пользователя | A | Meteor делает так же (`build.gradle#L66`); исключает дублирование классов. |
| D-4 | Навигация — через **публичный `baritone.api`** (`ICustomGoalProcess`, `IPathingBehavior`, `onPathEvent`, `IPathingControlManager`), обёрнутый в наш маленький интерфейс `Navigator`; без рефлексии во внутренности | A | Нужны события пути и проверка чужой задачи, которых нет в `IPathManager` Meteor. Рефлексию, как в `BaritonePathManager#L46-L58`, не используем. |
| D-5 | Перед автопроходом **не менять** глобальные настройки Baritone молча. Показать пользователю `allowBreak/allowPlace` и предложить временно выключить (с восстановлением при выходе) | A | Настройки глобальные и сохраняются; по умолчанию Baritone может ломать/ставить блоки. |
| D-6 | Поворот при установке — **видимый** (`clientSide=true`), без «тихих» пакетных поворотов | A | Прозрачность для игрока и правило «без скрытного поведения». |
| D-7 | Если Baritone занят (`isPathing()` или `mostRecentInControl()` — не наш процесс) — **не стартовать** без явного подтверждения | A | `setGoalAndPath` перезаписывает чужую цель (PathingControlManager#L96-L100). |
| D-8 | Анализ и оверлей работают **без Baritone**; навигационный модуль регистрируется только при `BaritoneUtils.IS_AVAILABLE` | A | Образец — `Modules.java#L573-L576`. |
| D-9 | Зависимость Meteor — release `0.5.8`, а не `0.5.8-SNAPSHOT` | A | Release есть в maven.meteordev.org/releases; воспроизводимость. |
| D-10 | Сборка на **JDK 21**, установленном параллельно с JDK 23 (без смены глобальных настроек); Loom/Gradle — версии шаблона 1.21.1 | A | Gradle 8.8/Loom 1.7 на JDK 23 падают (проверено); Fabric для 1.21.1 требует Java 21. |
| D-11 | Основной режим защиты: кандидат безопасен при **block light ≥ 1**; sky light и время суток не используются для «безопасно» | A | Overworld `monster_spawn_block_light_limit = 0` (TECHNICAL_RESEARCH §8.2, §8.6). |
| D-12 | Доп. профили (выкл. по умолчанию): «болотные слаймы» (block ≥ 8), «патрули/аванпост» (block ≥ 9) | A | §8.4. |
| D-14 | Факелы — **только из хотбара**; перемещение из инвентаря — позже и только явной настройкой | A | Спецификация FR-5; не трогаем чужие предметы. |
| D-15 | Порядок: подсветка (M2) → выделение/план (M3) → сопровождение (M4) → автопроход по выделению (M5) → без выделения + пещера (M6) | A | От безопасного к рискованному; каждая ступень проверяема. |
| D-16 | Выделение области — **два угла (кубоид)** с лимитом объёма; произвольная форма — позже | A | Проще, есть образец `Excavator`. |
| D-17 | Подсветка выключена по умолчанию, радиус 32, лимит боксов, бюджет скана ≤ 2 мс/тик; два уровня: чанки + отдельные места | A | Производительность; P-11. |
| D-18 | Зона анализа без выделения = окно по высоте (по умолч. −6/+8, «пещера» −24/+16) **+ связность по воздуху** от игрока + опция «не глубже 3 от поверхности» | A | Требование пользователя «не считать шахту под ногами»; P-2. |
| D-19 | Режим 2b обязательно ограничен: радиус (по умолч. 48), окно по точке старта, лимит факелов | A | P-5. |
| D-20 | Буферная полоса вокруг зоны (по умолч. выкл., 8–16 блоков) | A | P-1: мобы приходят снаружи. |
| D-21 | Свет переменных источников (печи, лампы, свечи, костры, медные лампы) по умолчанию **не** считается защитой | A | P-6. |
| D-22 | Недосягаемые опасные места выводятся отдельно, не игнорируются молча | A | P-3. |
| D-23 | Визуализация процесса: маркеры запланированных факелов, текущая цель, опасные места, HUD-статус с причиной остановки | A | Требование «наблюдать как в Baritone». |
| D-24 | «Неспавнящие» места определяются **ванильными проверками** на клиенте (`allowsSpawning`, `isClearForSpawn`, коллизия spawn box для zombie/spider/enderman), а не таблицей блоков; такие места не освещаются, граница с обычным полом обрабатывается автоматически | A | Требование пользователя; код 1.21.1 (§8.9); вики местами неточна (общее правило «прозрачности» в коде отсутствует). |
| D-25 | Классификация блоков: гибрид «свойства из API на BlockState + маленькие курируемые списки + контекстные проверки», слои L0–L4 | A | `BLOCK_CLASSIFICATION.md` §5, §9 |
| D-26 | Типы факелов: обычный (14) и soul (10, опционально); редстоун-факел не используется | A | luminance из кода; редстоун-сигнал |
| D-27 | Приседание при клике по интерактивным блокам — по умолчанию вкл. | A | `interactBlockInternal` вызывает `onUse` без приседания |
| D-28 | Буферы опасностей: лава 1 (путь) / 2 (позиция установки), огонь и кактус 1, магма — только «не стоять» | A | ваниль: соседство 1 |

Точки у края зоны пересчитываются свободно | P | Баг H4 «лазерная указка». Тест `previousPlanIsKeptAfterShiftingTheArea`: точки у игрока не сдвигаются, лишних факелов ≤ 2 |

| D-48 | Дальность — жёсткое правило обоих режимов: клик только если луч из глаз по фактическому направлению взгляда длиной `getBlockInteractionRange() − 0,1` попадает в грань опоры; точка клика = точка попадания луча. Факелы дальше руки и через блоки не ставятся никогда | A | Требование пользователя: «не ставить факелы, куда рука не дотянется — это видит античит»; сервер сам проверяет `canInteractWithBlockAt(pos, 1.0)` |
